这里的 **“编辑纪律”** 不是指代码格式规范（比如 tab/空格、命名规则），而是指 **OpenSeek 的 Agent 在修改文件时必须遵守的一套安全约束和工程原则**。

它位于工具系统报告里的：

> “文件工具链围绕一条主线：模型对文件系统的操作必须是可审计、可回滚、不破坏工程语义的。” 

简单说：

> **AI 可以改代码，但不能像一个拿着 root 权限的人一样随便改。每一次修改都必须知道自己改了什么、为什么能改、出了问题如何恢复。**

---

## 一、整体编辑流程（从模型提出修改到文件落盘）

可以理解为：

```
LLM 提出修改意图
        │
        ▼
选择工具
(edit / write / multi_edit / remove)
        │
        ▼
工具层安全检查
        │
        ├── 文件身份检查
        │
        ├── 路径安全检查
        │
        ├── 修改范围检查
        │
        ├── 语法检查
        │
        ▼
执行修改
        │
        ▼
验证工程状态
        │
        ├── 成功 → 保留
        │
        └── 失败 → 回滚
```

---

# 1. 首先：Agent 不能直接操作文件

模型本身只产生类似：

> “把 foo.mbt 里面这个函数改掉”

它不会直接调用 OS。

它必须经过工具：

* `read`
* `write`
* `edit`
* `multi_edit`
* `remove`

这些属于：

```
agent_tool/
    read
    write
    edit
    multi_edit
    remove
```

报告中列出的文件工具链包括这些组件。

---

# 2. read：先理解文件

一般流程：

```
模型：
我要修改 foo.mbt

↓

read(foo.mbt)

↓

返回：

第10行...
第20行...
第30行...
```

OpenSeek 的 read 不是简单 cat。

它会：

* 加行号
* 控制输出长度
* 防止上下文爆炸

例如：

> `read` 使用行号渲染，并且截断属于成功状态，而不是错误；默认最大 12000 字符，最高 50000。

为什么？

因为：

如果一个项目：

```
main.mbt
50000 行
```

AI 一次读进去：

* 浪费 token
* 容易迷失
* 增加错误修改概率

---

# 3. edit：最核心的“修改纪律”

重点来了。

`edit` 不是：

```
打开文件
↓
替换字符串
↓
保存
```

而是：

```
old_string
+
new_string
+
文件状态
+
约束检查
```

---

例如：

原文件：

```moonbit
fn hello() {
    println("hello")
}
```

AI 请求：

```
old:

println("hello")


new:

println("world")
```

工具执行：

---

## 第一步：确认 old 存在

如果：

```
old_string 找不到
```

失败。

因为 AI 可能理解错上下文。

---

## 第二步：确认匹配数量

例如：

文件：

```moonbit
println("hello")
...
println("hello")
```

两个地方都有。

AI 说：

替换：

```
println("hello")
```

工具会拒绝。

否则：

AI 以为改 A，实际改了 B。

---

## 第三步：限制替换规模

报告：

> `edit` 支持行锚定首匹配替换、空 old_string 插入/追加；有 replace_all_preview；站点 40 上限、双 24K 预算、算术防放大。

意思：

它防止：

```
一个小修改请求

↓

替换掉几万个地方
```

造成灾难。

---

# 4. write：创建新文件，但禁止乱覆盖

write 的规则更严格。

例如：

AI：

```
创建 hello.mbt
```

允许。

但是：

```
覆盖已有 main.mbt
```

通常拒绝。

报告：

> write 拒绝覆盖既有 `.mbt/.mbt.md`，经过 realpath 双检查。

原因：

假设：

```
main.mbt
```

是核心代码。

AI：

```
write(main.mbt)
```

如果允许：

旧代码直接消失。

所以：

```
已有源码
   |
   └── edit 修改

新文件
   |
   └── write 创建
```

这是核心纪律。

---

# 5. multi_edit：批量修改，但是事务化

比如：

修改：

```
a.mbt
b.mbt
c.mbt
```

普通方式：

```
改 a
成功

改 b
成功

改 c
失败
```

结果：

半完成状态。

OpenSeek：

```
multi_edit

↓

预检查全部修改

↓

全部通过

↓

一次提交
```

如果失败：

```
rollback
```

报告：

> multi_edit 跨文件批处理，先全量验证后写入；超过错误阈值会自动回滚整批。

类似数据库：

```
BEGIN TRANSACTION

修改 A
修改 B
修改 C

全部成功:
    COMMIT

失败:
    ROLLBACK
```

---

# 6. FileStateMap：为什么知道“谁创建的文件”？

这是编辑纪律最重要的一层。

OpenSeek 维护：

```
FileStateMap
```

记录：

```
文件:
    main.mbt

状态:
    Preexisting
    Created

digest:
    sha256(...)
```

报告：

> FileStateMap 记录每个文件是 agent 自建（Created）还是既有（Preexisting）；digest 证明内容未被篡改。

---

用途：

## 删除保护

例如：

AI 创建：

```
test.mbt
```

后来：

```
remove(test.mbt)
```

可以。

但是：

用户原本：

```
database.mbt
```

AI：

```
remove(database.mbt)
```

拒绝。

因为：

```
Created:
    可以删

Preexisting:
    不允许删
```

报告：

> remove 只删除有 digest 证明的 agent 自建文件，既有文件只能 edit 不能 remove。

---

# 7. 修改后：编译器验证

OpenSeek 有一个核心理念：

> 编译器就是最终裁判。

---

## write:

流程：

```
写入

↓

moonc syncheck

↓

语法错误？

↓

恢复
```

---

## multi_edit:

流程：

```
批量修改

↓

moon check --output-json

↓

统计错误

↓

超过阈值

↓

全部 revert
```

报告：

> write 用 `moonc syncheck` 预解析，multi_edit 用 `moon check --output-json` 错误计数自动回滚。

---

# 8. 最终形成一个“受控编辑闭环”

完整流程：

```
          用户任务

              ↓

          Agent 思考

              ↓

        read 获取上下文

              ↓

       选择 edit/write

              ↓

       文件安全检查

       ┌─────────────┐
       │             │
       ↓             ↓

   合法修改       拒绝修改


       ↓

    写入临时状态

       ↓

    编译检查

       ↓

 ┌───────────┐
 │           │
成功        失败

 │           │
commit     rollback

       ↓

   新 session event
```

# 为什么叫“编辑纪律”？

因为它体现的是一种 Agent 设计思想：

传统脚本：

> “AI 给我一段 patch，我执行。”

OpenSeek：

> “AI 是不可信操作者，必须通过受控工具修改世界。”

所以核心原则是：

| 原则        | 目的        |
| --------- | --------- |
| 来源追踪      | 知道文件是谁创建的 |
| digest 校验 | 防止误删/误改   |
| 语法门       | 避免破坏工程    |
| 事务回滚      | 避免半成品     |
| 禁止覆盖源码    | 防止 AI 毁库  |

这也是报告总结的四条：

1. 来源追踪
2. 语法门
3. 防写穿
4. 只删自建文件



---

如果和普通 Codex / Claude Code / Cursor 的文件编辑机制比较，OpenSeek 的特点可以概括为：

> **它不是“让模型拥有编辑权限”，而是“让模型申请编辑事务，由工具系统批准执行”。**
> 这也是它作为 Agent 基础设施，而不是简单代码助手的关键区别。
