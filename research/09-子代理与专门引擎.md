# OpenSeek 调研报告 09：子代理与专门引擎

> 范围：`agent_subrun/`（机制层，报告 07 已详述）、`agent_worker/`、`agent_explore/`、`agent_review/`

## 1. 子代理统一模式

worker 与 explore 是同构的"受限子代理"模式：

```
父回合 ──> capture 工具（control=true，注入 Ref[T?]）
    └─> 子进程回合（execute_kind 驱动一次受限工具集的 agent 回合）
         ├─ 只读/受限工具集 + 沙箱
         └─ 必须调用控制型提交工具（submit_*）产出结构化报告
父侧 parse_validated 信任边界重检（schema_version + 长度上限）
```

三层信任模型：**模型报告是建议性的，父控制器以 git 级 scope 校验为准**（types.mbt:2-6）。

## 2. `agent_worker/`（约 700 行）

```
pub struct WorkerReport { schema_version; status: done|partial|failed; summary≤2000; verification≤2000 }
WorkerSandbox { deny_roots; worker_root; worker_admin_dir }
default_worker_max_steps=300；default_worker_deadline_ms=2_700_000（45 分钟）
```

- **工具集**：read、shell（WorkerSandbox 沙箱）、edit/multi_edit/write/remove（共享 `FileStateMap` + `WriteScope`）、`submit_result` 控制工具；
- **刻意不放 `run_moonbit`**——其 snippet runner 可能写出 worker tree（tool.mbt:179-184）；
- 报告字段全部 validate（types.mbt:56 起的样板循环）。

## 3. `agent_explore/`（约 800 行）

```
pub struct ExploreReport { answer≤8000, citations≤20, unresolved≤1000 }   // 全字段 validate
default_explore_max_steps=100；deadline 10 分钟
```

- **工具集**：read、shell（read_only=true + scratch lab）、`run_moonbit`、`submit_answer`——无编辑工具无嵌套子代理；
- **失败契约**：无报告/超时/预算耗尽 → is_error 结果引导父代理直接读文件，**绝不弄断 turn**（tool.mbt:42-44）；
- explore 无 deadline 常数导出（`default_explore_deadline_ms` 是 `let` 非 `pub`）。

## 4. `agent_review/` — 编译基准代码审查引擎（约 950 行）

```
pub struct Finding { file; line: Int?; severity: String; category; title; detail; suggestion: String? }
pub struct ReviewScope { base; head; files }
pub struct ReviewReport { schema_version: Int; scope; findings; summary; stats: ReviewStats }
pub async fn run_review(api_key, model, base, workspace_root?=".", max_steps?=120, thinking?, api_url?) -> ReviewReport
pub async fn run_goal_audit(goal~, baseline~, api_key~, model~, max_steps~, ...) -> ReviewReport?
pub fn ReviewReport::validate(self) -> Array[String]
pub fn ReviewReport::digest(self) -> String
```

### 4.1 架构

- 引擎**不直接调编译器**：通过 `@agent_subrun.execute_kind` 在本进程驱动一次 `@agent.run_turn_in_scope`，工具集只有 `read`、`shell(read_only=true)`、`run_moonbit`、`submit_review`；
- 模型**必须**调用 `submit_review` 提交结构化报告：它是 `control=true` 的 capture 工具，JSON Schema + `parse_submission` 双重校验，非法输出返回错误让模型重试；未提交则抛 `ReviewError`（engine.mbt:57-62）；
- 编译器调用发生在模型自主执行 `run_moonbit`/`shell` 时——审查 prompt 强制"以 `moon check --target all`/`moon test` 为 ground truth"；
- JSON 形状即集成边界：全部 `derive(ToJson, FromJson)`，刻意保持扁平、字符串化（severity 是 `String` 而非枚举）；
- audit digest 硬性上限（`digest_max_findings=10`、`digest_max_chars=4000`，audit.mbt:108-117）。

### 4.2 设计决策

1. **结构化输出靠工具强制而非事后解析**——"无报告即失败"由 control 工具 + 校验实现；
2. 只读是 best-effort：`moon check` 的 pre-build 可能生成源码（注释承认）；
3. CLI 层（cmd/openseek/review.mbt:25）固定 `V4Pro` 模型、退出码 0/1/2（2=有 blocker）。

### 4.3 已知不足

- severity 校验在 `validate()`（exports.mbt:39-43）与 JSON Schema enum（submit.mbt:75）**两处重复定义**，有漂移风险；
- `default_review_max_steps=120` 被 CLI 覆盖为 `@agent.unbounded_max_steps`（review.mbt:63），两处默认不一致。

## 5. 跨层观察

1. 三套受限工具集（worker/explore/review）是同一模板的三次实例化，validate 样板复制粘贴——可提取公共"受限子代理"骨架；
2. **deadline 常量三处分散**：explore 600s / worker 2700s / gate（`GateDeadlineMs=900_000`，15 分钟）在三个文件里各自定义；
3. 报告的"建议性 + 父侧 git 证据校验"双层信任是安全设计核心：模型撒谎无害，因为 capture 的产物最终要过 scope/git 检查；
4. review 引擎"用 agent 审代码"（让模型自己跑 moon check/test）比"宿主侧硬解析诊断"更灵活，代价是成本与不可确定性——这是刻意的架构选择。
