# OpenSeek 调研报告 08：终端 UI

> 范围：`cmd/tui/`（16 文件 6,231 行）、`tui/`（46 文件 6,638 行可复用框架）

## 1. 两层结构

```
tui/（可复用框架，与引擎无关）
  with_ui / Ui / Config / TranscriptItem / completion / slash / style / internal/{composer,viewport,render,...}
        ↑ 消费
cmd/tui/（OpenSeek TUI 客户端）
  EngineClient（管理 serve 引擎进程）
  State/Msg/Cmd（TEA 风格状态机）
  scheduler（/loop 定时派发）
  loop.mbt 2,142 行（主消息循环）
```

## 2. `tui/` 框架层

### 2.1 核心 API

```
pub fn with_ui[T](config?, body: async (Ui) -> T) -> T      // ui.mbt:131
pub struct Ui {
  commands: @task.Queue    // 串行化重绘
  events: @aqueue.Queue
  pending_submissions: Int // 防调度器误判的关键
}
Ui::append_item(item: TranscriptItem) / set_live_view(status~, activity~, queued_inputs~) /
   input_idle() / read_event() / submission_delivered()
pub enum TranscriptItem { Input | Response | ToolCall | Notice | Thought | Error }  // core/transcript.mbt:46
pub struct Config::new(esc_timeout_ms?, composer_max_rows?, slash_commands?)
```

### 2.2 架构

- **三层渲染**：`internal/composer`（多行输入模型：逻辑行/视觉行/文本光标）、`internal/viewport`（终端尺寸跟踪、scrollback 回放、frame cache）、`internal/render`（surface→diff 渲染）；
- 所有重绘走 `commands.wait()` **串行化**；tty reader 任务把事件经 `handle_tty_event` 语义化后放入 events 队列；
- `with_ui` 开 tty raw 模式 + **kitty "disambiguate" 键盘增强**，`with_entered` 保证成败都恢复终端；
- `input_idle()` + `pending_submissions` 精确配对提交窗口——防调度器超车刚按下的 Enter（terminal.mbt:141-156）。

### 2.3 已知不足

- **`ui.mbt`/`input.mbt`/`terminal.mbt` 零单元测试**——键盘处理（627 行 input+completion 的主要逻辑）只有间接覆盖；
- `completion.mbt`（627 行）只有 65 行测试，与 `render.mbt`（284 行 + 538 行测试）严重不对称；
- `Ui::redraw` 缺 viewport 时 `abort()`——内部一致性 guard，但生产路径上任何生命周期 bug 直接崩溃而非报错；
- kitty 增强请求失败静默降级（合理但无日志）；
- config 对非法参数（负 esc_timeout）静默回落默认值，无警告。

## 3. `cmd/tui/` 客户端

### 3.1 核心类型

  process + WriteToProcess + run 簿记（latest_run/run_open）+ pending_goal_acks

### 3.2 消息循环架构（`loop.mbt` 2,142 行）

`run_app`（main.mbt:373）→ `run_message_loop`（loop.mbt:818）单消费者循环：

```
drain 消息队列 → update(state, msg) 产出 Cmd 数组
→ scheduler_maybe_fire（/loop 唯一派发点）
→ 执行 Cmd → refresh_ui
```

关键机制：

1. **run_id 防陈旧**：`State::owns_run`（state.mbt:164）丢弃来自已取代 run 的消息——整个 TUI 一致性的基石；引擎死亡时 stdout reader 合成 `AgentError`（engine_exit_without_result），引擎重启（respawn）依赖 durable session；
2. **`read_ui_events` 与 `tick_ui` 独立后台任务**；`ui.submission_delivered()` 精确配对提交计数，防 `/loop` 超车刚按下的 Enter（loop.mbt:12-14）；
3. **Esc 刻意不当作 Interrupt**（input.mbt:186-199）：kitty 协议下拆包的幻影 Esc 会误杀任务；
4. **Ctrl-C 三级语义**：空闲退出；运行中 cancel；第二次 Ctrl-C kill 引擎（loop.mbt:696-712）；
5. **stderr 有界捕获**（`drain_stderr_capped`，loop.mbt:54，8KB cap）：既给诊断又防管道写满死锁；
6. 背景 `!` 命令 fire-and-forget；其输出经 `@command_context.encode` 包成 `<user_shell_command>` 信封作为 command context 交给引擎（loop.mbt:731）；
7. 引擎 env 全量覆盖继承的 `OPENSEEK_*` 变量（engine_client.mbt:170-179）；
8. `/loop` 调度器（scheduler.mbt）：interval 语法 `300/30s/5m/2h`、最小 10s、默认 20 次上限、失败自动暂停；`parse_loop_interval` 先除后乘防溢出（:350）。

### 3.3 已知不足

- **command context 投递 fire-and-forget**：引擎接受后崩溃（既无 steer_applied 也无 session_error）时输出静默丢失——engine_client.mbt:358-379 明确承认是"故意权衡"，但用户看到 `!` 卡片而 resume 后没有内容；
- **`engine_command_launchable`（main.mbt:407）无超时**：`--help` 探测进程挂起会让 TUI 启动永久卡住（`collect_output_merged` 无 deadline）；
- `decode.mbt` 的 `mcp_safe` 是第三份转义清洗拷贝（与 main.mbt:918、mcp.mbt:151 重复）；
- 事件解码对未知 `steer kind` 默认当 Prompt（decode.mbt:29-34）——与 serve 端兼容默认呼应，但新版引擎加 kind 时旧 TUI 会误读；
- `goal.mbt` 的 `clear` 总是发 tombstone（即使无 goal）——产生无意义事件；
- `pending_goal_acks.search(goal)` 线性扫描（量小可接受）。

## 4. 跨层观察

1. TUI 是全书并发心智负担最重的模块：run_id 防陈旧 + 唯一派发点 + 输入空闲判定 + 提交计数配对，四重机制共同保证"UI 事件永不超车、永不过期"；
2. "引擎是外部进程 + JSONL 协议"的架构让 TUI 可以任意 respawn 引擎而不丢会话——durable session 的收益在这里兑现；
3. 测试严重不对称：渲染层（render 538 行测试）与调度器有测试，但键盘/输入/终端层零测试——这类代码恰恰是回归重灾区；
4. `loop.mbt` 2,142 行单体是下一轮拆分候选（与 turn_loop.mbt、sandbox.mbt 并列全书三大单体）。
