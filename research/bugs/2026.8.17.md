基于这次测试的全程表现，我提炼出该 Agent 工具链在**底层执行、编辑引擎、调度策略**三个层面暴露的 3 个核心问题，并给出对应的解决思路（仅思路，不涉及具体实现）：

---

### 问题 1：Shell 执行层——对 Windows 环境的适配存在“硬伤”

- **表现**：
  - 大量命令抛出 `moonbitlang/core/encoding/utf8.Malformed.Malformed`（MoonBit 运行时内部的 UTF-8 解码错误）。
  - 每次执行 `shell` 都弹出独立的 CMD 窗口，视觉上“抽风”。
- **根因**：
  - 工具链内部的 Shell 模块在处理 Windows 控制台代码页（如 GBK/UTF-8 混用）和非 ASCII 字符（中文文件名/输出）时，**默认字符集假设过于理想化**（假设系统纯 UTF-8）。
  - 子进程创建时未设置 `CREATE_NO_WINDOW` 标志，导致每个命令都申请一个新控制台宿主。
- **解决思路**：
  - **编码适配层**：在执行命令前，强制将子进程的输入/输出代码页临时切换为 UTF-8（`chcp 65001`），并将 stderr 的原始字节流强制转码后再交由解析器处理，避免因解码失败直接崩溃整个 Shell 会话。
  - **进程窗口隐藏**：在 Shell 工具的底层实现中，为 Windows 平台单独配置进程创建标志，默认隐藏窗口（无界面运行），减少干扰。

---

### 问题 2：文件编辑层——“精确字符串匹配”策略过于僵化，缺乏容错

- **表现**：
  - 连续多次 `edit` / `multi_edit` 失败，报错 `old_string not found`，即使肉眼看起来内容完全一致。
  - 被迫使用 `write`（全量覆写）绕过匹配机制，虽然在 `.md` 上可行，但在 `.mbt` 源码上会被禁止。
- **根因**：
  - 编辑器采用**绝对二进制级别的逐字匹配**，对换行符（`LF` vs `CRLF`）、行首/行尾空格、全角/半角标点差异 **零容忍**，没有模糊匹配或归一化层。
  - 没有区分“源码文件（`.mbt`）”和“文档文件（`.md`）”的编辑策略——文档对细微格式差异本应更宽容。
- **解决思路**：
  - **引入归一化比较层**：在执行匹配前，将 `old_string` 和目标行进行“等价归一化”（统一换行符为 `LF`，去除行尾空格，统一 Unicode 正规化形式），若归一化后匹配再应用修改，降低因格式差异导致的误报。
  - **文档类文件降级策略**：对 `.md`、`.txt` 等非语法检查文件，当精确匹配失败超过 2 次后，**自动降级为“行内替换”或“上下文块替换”**（基于相邻固定行的模糊定位），而非直接放弃。

---

### 问题 3：Agent 调度策略层——工具选择（`edit` vs `write`）过于保守，缺乏智能预判

- **表现**：
  - 在明知文档中存在多处大面积结构性错误时，依然优先尝试逐行 `edit`，导致大量无效的往返尝试（retry loop），浪费时间和 tokens。
  - 直到多次失败后才切换为 `write`，反应滞后。
- **根因**：
  - Agent 的系统 Prompt 对 `write` 工具的限制描述（“Overwriting existing source file is rejected”）产生了**过度威慑效应**，导致 Agent 优先使用更“安全”但更脆弱的 `edit`。
  - 缺乏对“修改规模”的预判：当需要修改的行数占比超过一定阈值（如 >30%）或跨多个不连续块时，未自动切换为“重建整个文件”。
- **解决思路**：
  - **引入“编辑意图规模检测”**：在决定工具前，Agent 预估改动范围。若改动跨越文件总行数的 20% 以上或涉及 5 个以上不连续块，**优先推荐 `write` 重写**（对于文档类文件），或推荐 `multi_edit` 先做合并尝试。
  - **给 `write` 工具增加“安全覆写”模式**：允许对非源码文件（即非 `.mbt`、`.mod`、`.pkg`）无条件使用 `write`；对源码文件，则要求先执行 `moon check` 校验新内容的语法合法性再落地。

---

### 总结
这套工具链的逻辑核心是**“编译级安全优先”**，这本身是优点。但在 Windows + 文档编辑场景下，**过于苛刻的字符串匹配**和**缺乏环境感知的子进程**把“安全”变成了“脆皮”。 

优化的核心思路是：**为“文档”和“源码”解耦工具策略，为“Windows”和“Unix”解耦执行环境，让工具该灵活时灵活，该严格时严格。**
