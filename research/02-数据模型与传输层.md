# OpenSeek 调研报告 02：数据模型与传输层

> 范围：`deepseek/`、`deepseek/client/`、`jsonrpc/`、`protocol/` + `protocol/emit/`
> 依赖：除 client 外均为纯逻辑或 leaf 模块；client 依赖 `moonbitlang/async`、`async/http`、`async/io`

## 1. `deepseek/` — 纯数据层（约 700 行源码 + 700 行测试）

### 1.1 核心类型

```
enum Model { Deepseek(DsVariant); Kimi(KimiVariant) }     // deepseek.mbt:17
  DsVariant { V4Flash; V4Pro } / KimiVariant { K27Code; K27CodeHighSpeed }
  // 各有 context_window（V4 系 1M、Kimi 256K），供自动压缩守卫使用
enum Role { System; User; Assistant; Tool(String) }       // deepseek.mbt:135
  // Tool 携带 tool_call_id
struct ChatMessage { role: Role; content: String; tool_calls: Array[ToolCall]; reasoning_content: String? }
struct ToolDefinition { name; description; parameters: Json; strict: Bool }
struct ToolCall { id; name; arguments: String }           // arguments 是不透明 JSON 字符串
struct ChatResponse { content; reasoning_content; tool_calls; usage: Usage }
enum ThinkingMode { No; High; Max }
enum ResponseFormat { JsonObject }
```

### 1.2 编解码实现

- **解码**（`json_decode.mbt`）：手写对象模式匹配；`ToolCall::from_json` 用 `JsonPath`（`path.add_key`）逐层定位缺哪个字段；`ChatResponse::from_json` 只取 `choices[0]`，`content: null`→空串、`tool_calls: null`→`[]`、缺 `usage`→`Usage::empty()`；错误经 `@json.JsonDecodeError` 抛出。
- **编码**（`json_encode.mbt`）：`encode_chat_request(tools?, thinking?, stream?, response_format?, model?, messages)` 统一入口——Kimi 不发 `thinking` 字段；`stream=true` 附 `stream_options: {include_usage: true}`；assistant 空 content+tool_calls 编为 `content: null`；`reasoning_content` 仅 Kimi 回传（`reasoning_json_fields`，DeepSeek 侧内存中携带也会被静默丢弃，测试显式固定该行为）。
- **API key**（`api_key.mbt:27-41`）：`Model::api_key` 把 CLI 选项解析统一为一组有序 match 臂（`--api-key` 优先于 provider 专属选项），消除了跨 main 的复制漂移。

### 1.3 已知不足

| 问题 | 位置 | 说明 |
| --- | --- | --- |
| Usage 解码截断小数 | `json_decode.mbt:21-25` | `.to_int()` 把 1.5→1，"伪造" token 计数；与 `protocol/parse.mbt:299-304` 显式拒绝小数的严格 `int()` 不一致 |
| 不解码 finish_reason | `ChatResponse` | 调用方只能靠 `tool_calls` 是否为空推断结束原因 |
| DeepSeek reasoning_content 静默丢失 | `json_encode.mbt:9-18` | 有测试背书，但属易误用 API |
| api_key 不校验归属 | `api_key.mbt` | `--api-key` 对 Kimi/DeepSeek 一视同仁 |

## 2. `deepseek/client/` — HTTP 传输层（native-only，约 600 行）

### 2.1 API

```
pub struct Client { priv api_key: API_KEY; model; api_url; thinking; retry_attempts; retry_backoff_ms; idle_timeout_ms }
  derive(Debug(ignore=API_KEY))
pub async fn Client::chat(Self, Array[ChatMessage], tools?, response_format?, stream?: StreamHandler) -> ChatResponse
pub struct StreamHandler { priv on_content_delta: async (String)->Unit; priv on_reasoning_delta: ... }
```

默认 URL：DeepSeek `https://api.deepseek.com/chat/completions`、Kimi `https://api.moonshot.cn/v1/chat/completions`。

### 2.2 关键机制

1. **重试**（`client.mbt:141-165`）：`@async.retry` + `ExponentialDelay(500ms, ×2, cap 60s)`；`RetryableApiError` 私有 suberror 标记可重试（传输错误、HTTP 429、5xx）；其它 4xx 立即失败；bail（流式已产事件）|| 取消 || 普通 Failure || URI 解析错误不可重试。预算耗尽后以普通 `fail(message)` 重抛，私有类型不出包。
2. **流式 SSE**（`stream.mbt`）：钉死 `Accept-Encoding: identity`（防压缩中介重缓冲 SSE 分片）；写请求体后 `with_idle_timeout` 限时等响应头；按行读 `data:` 片段，空行触发 `flush_sse_event`——先调 `on_stream_event`（把"已产生任何事件"计入重试 bail）再解析 JSON；`[DONE]` 提前返回；无终止符 EOF/超时也先 flush 再抛可重试错误。
3. **StreamAccumulator**（`stream.mbt:23-38`）：`StringBuilder` 累积 content/reasoning；`StreamToolCall` 按 `index` 归并 tool_call 增量（`apply_tool_call_delta`）；最后把累积值重新组装成标准 envelope 走 `@json.from_json` **复用解码逻辑**——这是很干净的设计。
4. **空闲超时**：默认 120s，按"行"计时（`read_stream_line` 用 `with_timeout_opt` 包 `read_until("\n")`），非正数禁用。

### 2.3 设计决策

- 流式一旦产出任何事件（含 tool_call 增量、usage）即放弃重试——避免重复内容/重新生成工具调用（client.mbt:193-209）；
- 2xx 但体非法的响应视为最终裁决不重试（"已计费"论）；
- API key 经 `Debug(ignore=API_KEY)` 脱敏（client_test.mbt:22-37 验证）。

### 2.4 已知不足

- **错误文本含完整响应体**（client.mbt:225）：若被配置错误的代理回显请求头（含 Authorization），key 可能泄入日志；
- `retry_attempts=0` 时 `max_retry=-1` 语义未文档化；
- 无 `max_tokens`/`temperature` 参数，无法约束生成长度；
- SSE 解析只认 `data:` 行，忽略 `event:`/`id:`/`retry:`——够用但非通用 SSE 客户端。

## 3. `jsonrpc/` — JSON-RPC 2.0 客户端（native-only，约 420 行）

### 3.1 架构：双常驻任务

```
pub(open) trait Transport { async fn send(Self, Json)->Unit; async fn recv(Self)->Json?; fn close(Self)->Unit }
pub async fn Client::request(Self, method_~: String, params~: Json) -> Json
pub async fn Client::notify(Self, method_~, params~) -> Unit
pub async fn Client::run_writer(Self) / run_message_pump(Self)   // 调用方 spawn
```

- **reader**（`run_message_pump`）独占 `transport.recv`，按 `pending: Map[Int, @async.Queue[Result[Json, ResponseError]]]` 把乱序回复投递到对应 inbox（client.mbt:58）；MoonBit 协作式 async + 单一 reader 使 Map/计数器无锁。
- **writer**（`run_writer`）独占 `transport.send`，从有界 outbox（`OutboxCapacity=1024`）排空；所有出站消息（request/notify/reader 对 peer 请求的应答）都经 outbox 排队，**reader 永不阻塞写**（防背压死锁）。
- `request` 先注册 inbox 再入队（client.mbt:108-112），保证并发 close 也能投递 `Closed`。

### 3.2 协议分类（protocol.mbt）

- `classify_incoming`：有 `method` 字段即 peer 请求（带 id）或通知（无 id，含 id:null 也算请求）；
- 回复 id 必须**精确整数往返**（`int_reply_id`，防 `to_int` 截断 1.5→1 导致误路由）；
- `parse_outcome`："error 非 null 优先于 result"，`error:null`+result 算成功；`parse_error` 缺省 code=0/message=""；
- `dispatch`：处理 peer `ping`（答空结果）和批处理数组（逐元素路由）。

### 3.3 已知不足

- `request` 无内置截止时间——transport 永不 EOF 时会永久挂起（有文档声明，靠调用方包 `with_timeout`）；
- `on_notification` 同步跑在 reader 任务上，阻塞 handler 会卡住全部路由；
- `build_request` 用 `id.to_double()`，id 超 2^53 精度损失（理论问题）；
- writer 逐条发送、不组批——并发请求无 JSON-RPC batch 优化；
- `notify` 在 outbox 已关闭时静默丢消息。

## 4. `protocol/` + `protocol/emit/` — 引擎事件流 wire 契约

### 4.1 模块性质

`protocol/` 是**独立模块** `bobzhang/openseek_protocol`（有自己 `moon.mod`），leaf 依赖仅 `core/json`，可编译到 js/wasm；`emit/` 因依赖 native-only 的 `tonyfettes/xlog` 单独成包。

### 4.2 wire 格式

引擎 stdout 的 JSONL 行 = `@xlog` envelope（timestamp/level/source）+ 字段**提升到顶层**的平铺事件：

```json
{"timestamp":"…","level":"INFO","source":"agent/turn_loop.mbt:392:9","event":"assistant_delta","content":"Hel"}
```

`Event` 是约 40 个变体的 `pub(all) enum`（event.mbt:14-132），每个变体**自持日志级别**（emit.mbt:8-34：AgentSetupFailed/TurnFailed/CompactionFailed 等=Error，MCP 相关大部分=Warn，其余 Info）；`Event::to_json` 是唯一编码器；`parse` 是逆解码器。`emit` 带 `#callsite(autofill(loc))` 使 `source` 指向真正报事件的调用点，且**先查 `@xlog.event` 过滤再序列化**。

### 4.3 严格性设计

- 可选字段写 `null` 而非省略（`or_null`，规避 MoonBit `Some(v)` 被编码成单元素数组的坑）；
- `parse` 对"引擎从未省略过的字段"一律 required，只对三个经 `git log -S` 验证的历史追加字段（`steer_applied.kind`、`session_started.workspace_root`、`tool_result.brief`）做缺省；
- `int()` 拒绝小数 token 计数；
- `Usage` 故意是**独立于 `@deepseek.Usage` 的类型**（防厂商字段改名静默改变 wire 契约），且只 derive `ToJson` 不 derive `FromJson`（防第二个不一致的解码器）；
- `Command`（stdin 方向：Prompt/Steer/Compact/Cancel/GoalSet/GoalClear）parse 返回 `Result` 而非 `Option`（不可读的命令必须让控制器知道）。

### 4.4 已知不足

- 新增一个 Event 变体需同步改 3 处 exhaustive match（to_json/parse/level），靠往返测试兜底；
- README 自述：协议没有独立于日志的 sink，`reasoning_delta` 曾因日志噪音被删、连累客户端"实时思考"视图；
- `parse` 对未知事件名返回 `None` 静默忽略——对新引擎宽容，但旧客户端会无声丢事件。

## 5. 跨层观察

1. **严格度不一致是系统性问题**：`deepseek.Usage` 截断小数 vs `protocol.Usage` 拒绝小数——token 计数是上下文压缩守卫的输入，这一不一致值得统一；
2. **"复用解码器"模式**（流式累积器重组 envelope 走 `from_json`、emit 先过滤后序列化）是全库贯彻的良好实践；
3. **错误分类**（可重试/不可重试、可恢复/不可恢复）是本库最细致的部分，各层一致遵循；
4. 密钥脱敏只做了 `Debug` 脱敏，错误文本回显响应体是残留的泄露通道。
