问题 4：Shell 工具缺乏“静默执行”模式（Windows 专属痛点）
表现：每次调用 shell 工具，都会在任务栏弹出新的命令行窗口（CMD 或 PowerShell），飞快出现又消失。连续调用时就像“弹窗轰炸”，严重影响注意力。

根因：工具链的 Shell 实现没有区分“交互式终端”和“后台执行”的视觉策略。在 Windows 下，创建子进程时未设置 CREATE_NO_WINDOW 或 DETACHED_PROCESS 标志，导致每个命令都申请一个控制台窗口宿主。

解决思路：在 Shell 工具的底层实现中，增加一个全局配置项 hide_window: bool，默认根据操作系统和工具调用上下文自动设置为 true（即 Windows 下默认静默）。同时，允许 Agent 在调用时显式指定 show_window: true（仅用于需要人工干预的命令，如 vim、nano）。这样既能消除弹窗，又不牺牲必要时查看交互界面的能力。

问题 5：工具调用失败时，错误信息“链式污染”严重
表现：当 Select-String 或 Get-Content 等命令因编码问题失败时，返回的错误信息是 moonbitlang/core/encoding/utf8.Malformed.Malformed 这种MoonBit 内部的运行时异常，而非用户友好的“命令执行失败：原因”。这使得 Agent 和用户都无法快速定位问题到底出在命令本身、管道，还是字符集。

根因：Shell 工具在执行外部命令时，如果外部进程输出非 UTF-8 字节流，且后续处理层（MoonBit 的 encoding/utf8 模块）未能妥善处理 BOM 或非法序列，会直接抛出 Malformed 错误并中止整个工具调用，而不是先捕获原始字节再尝试解码。

解决思路：在 Shell 工具的输出捕获层增加“原始字节缓冲区”，不立即解码，而是先判断系统代码页（Windows 下通常为 GBK/CP936），使用相应的编码进行转换。若转换失败，则输出十六进制转储和原始二进制内容，决不允许内部解析器异常泄漏到工具结果中。同时，为工具调用者（Agent）提供 raw_output: bool 选项，允许跳过解码直接获取字节流。

问题 6：工具调用缺乏“上下文感知”的缓存机制
表现：在执行 ls、find、Get-ChildItem 等纯查询命令时，即使目录内容未变，每次调用都会重新执行文件系统遍历，导致频繁的 I/O 抖动和命令弹窗重复出现。

根因：所有 shell 调用都是无状态的，没有内置缓存层。Agent 无法告知工具“此目录在上一步刚查过，如果未变动请返回上次结果”，也无法利用文件的 last_write_time 或 inode 变更标记来做增量判断。

解决思路：为 Shell 工具引入一个轻量级会话级缓存，以命令字符串 + 工作目录作为键，缓存输出结果和文件系统的“变更检测指纹”（如所有文件的 last_write_time 总和）。在执行新命令前，先检查缓存键和指纹，若一致则直接返回缓存结果，不重新启动子进程。缓存生命周期限制为当前对话轮次，避免内存泄漏。此策略可大幅减少不必要的弹窗和 I/O 开销。

问题 7：编辑工具（edit/multi_edit）缺乏“自动修复换行符”的能力
表现：因为 LF vs CRLF 的不匹配，导致大量 old_string not found 错误。Agent 被迫手动调整 old_string 中的换行符，或放弃使用 edit。

根因：编辑器在匹配前未对目标行进行换行符归一化。默认假设文件使用 LF，但对 Windows 上的 Git 仓库（通常配置 autocrlf=true）产生的文件，常出现 CRLF，导致匹配失败。

解决思路：在 edit 工具的匹配预处理阶段，先将 old_string 和目标文件内容中的换行符统一转换为 LF（或统一为文件当前使用的换行符风格）后再进行比较。同时，在应用修改时，保留原文件的换行符风格（即使用原文件的换行符来写入 new_string）。这样既解决了匹配问题，又不会破坏团队约定的代码格式。

问题 8：对“源文件”与“文档文件”的区分策略在编辑工具中过于隐式，且文档不透明
表现：用户（和 Agent）并不清楚哪些文件被禁止 write，哪些允许。Agent 仅凭系统 Prompt 中的描述判断，但描述较为模糊（仅提到 .mbt、.mbt.md 拒绝覆写），导致 Agent 在面对 .md 时依然畏首畏尾，不敢直接 write，反而陷入 edit 死循环。

根因：工具链没有提供一个明确的 API 或反馈机制（例如在 write 结果中明确提示“此文件类型允许覆写”），Agent 只能靠猜测和试探来决策。

解决思路：让 write 工具在拒绝时给出更具体的错误码和允许的文件类型列表（如 allowed_types: .txt, .md, .json, .toml），并允许 Agent 在调用 write 时携带一个 force: true 参数（仅对文档类文件生效，源码文件无论如何拒绝）。同时，在系统 Prompt 中直接给出清晰的策略表：哪些文件允许 write，哪些必须用 edit，哪些必须通过编译器反馈来改。

总结（新增）
这次测试暴露出的不仅仅是“弹窗”和“匹配失败”这些表面现象，更深层的问题是：

环境适配层缺失（Windows 字符集、进程窗口、换行符）。

状态管理不足（无缓存、无指纹检测）。

决策信息不透明（Agent 不知道哪些工具能做什么，只能盲目试错）。

改进方向不是让工具更“智能”，而是让工具在底层更健壮、反馈更明确、策略更清晰，让 Agent 能基于确定性规则做决策，而不是靠“碰运气”。
