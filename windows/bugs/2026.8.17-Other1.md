问题 4：任务反馈机制——长任务无进度指示，用户感知为“假死”
表现：

在执行 read 8 个文件或 shell 查询多目录时，前端界面长时间无任何反馈，用户只能看到“处理中...”或空白，容易误以为工具卡死。

尤其在 Windows 下弹窗一闪而过，用户无法追踪命令执行到哪一步。

根因：

工具链缺少细粒度的进度回调机制。每个工具调用只有“开始”和“结束”两个状态，中间状态不对外暴露。

对用户而言，一串连续的 Shell 调用在底层是并行的，但前端 UI 只会显示最后一个结束的状态，整个过程看起来像“要么没反应，要么突然全跳出来”。

解决思路：

引入“命令队列化 + 实时状态流”：将每个 shell 调用的生命周期分解为 pending → running → finishing → done，并以增量方式推送给前端（例如通过 Server-Sent Events）。用户可以看到当前正在执行哪条命令、已执行几条。

为长耗时操作增加“心跳提示”：例如当 read 一个大文件或 shell 执行 tree 超过 5 秒时，自动发送“仍在处理中...”的保底提示，避免界面完全无响应。

问题 5：并发调用的副作用——大量独立 Shell 调用导致系统资源浪费
表现：

在探索阶段，我并行发起了 10+ 个 shell 调用（分别查 moon.mod、查文件数、查目录存在性等），每个调用都启动一个独立的子进程，消耗系统句柄和 CPU 时间。

这些命令大多相互独立，但工具链没有提供“批处理”或“脚本块”的高级优化，导致用户侧弹出大量窗口。

根因：

工具链的设计哲学是“每个 shell 调用对应一个命令”，鼓励 Agent 通过多次小调用来获取信息（降低单次命令的复杂度）。

但 Windows 下创建进程的开销较大，大量并行进程会加剧窗口闪烁和系统响应变慢。

解决思路：

增加“复合 Shell 命令”支持：Agent 可将多个独立命令用 && 或 ; 拼接成一个长命令，但工具链不限制命令长度。更优的是工具提供 batch_shell 接口，接受一个命令数组，在一个子进程内顺序执行并收集所有输出，减少进程创建次数。

结果缓存：对短时间内重复的查询（如多次 ls 同一目录），工具可提供轻量级缓存（仅限当前会话），减少真实文件系统访问。

问题 6：多文件编辑的事务性不足——“部分成功”导致状态不一致
表现：

当我尝试用 multi_edit 一次修改多个文件时，如果其中某个文件的某个编辑失败，整个 multi_edit 会全部回滚（no changes applied），而不是仅跳过失败项。

在本次测试中，因为两处匹配失败，导致整个 9 个编辑全部作废，浪费了之前的准备工作。

根因：

工具链采取了“原子性”设计：要么全改，要么全不改，以避免出现“文件 A 改了，文件 B 没改”的中间状态。

但在大型重构中，某些编辑失败可能只是因为单个字符串匹配问题，若完全回滚反而需要 Agent 重新组织所有编辑，效率低下。

解决思路：

引入“最佳努力（Best-effort）”模式：允许 Agent 在调用 multi_edit 时指定一个容错参数，如 ignore_missing: true，则对于匹配失败的编辑项，工具跳过并记录失败原因，继续应用其他编辑，最后返回哪些成功、哪些失败。

改动预览与确认：在正式应用前，工具可返回一个“拟修改的差异预览”，Agent 可先行检查是否有明显错误，再决定是否提交，减少因匹配错误导致的原子回滚。

问题 7：跨平台路径处理的隐式陷阱
表现：

在 Windows 下，我被迫使用了大量的反斜杠（\\）和双引号转义，导致命令字符串冗长且容易出错（例如 Get-ChildItem -Path .\\window\\, .\\commands\\）。

read 工具接受绝对路径时用了 E:\\...，但返回的内容中路径显示正常，说明内部有转换，但 Agent 层仍需手动构造转义。

根因：

工具链的 shell 命令直接透传给操作系统的命令行解释器（如 cmd.exe），因此 Agent 必须遵守 Windows 的路径和转义规则。

但对于 read、edit 等文件工具，它们是在 Agent 沙箱内部执行的，本可以采用平台无关的路径格式（如使用 / 自动转换），但并未提供统一抽象。

解决思路：

统一路径输入格式：工具层无论底层操作系统，都接受 POSIX 风格路径（/），内部自动转换为目标平台的本地路径。这样 Agent 只需始终使用 /，无需关心反斜杠和转义。

提供“路径安全工具”：提供一个 join_path 或 normalize_path 内部函数，Agent 可通过 run_moonbit 调用它来构造正确路径，避免手写字符串拼接。

问题 8：错误信息的“噪音化”——技术栈泄露干扰诊断
表现：

当 tree 命令失败时，错误消息为 error running shell: moonbitlang/core/encoding/utf8.Malformed.Malformed，这个错误直接暴露了 MoonBit 运行时内部的异常类型，但对用户（或 Agent）几乎没有诊断价值。

真正的错误原因（tree 参数错误）被埋没在底层编解码异常中，导致我一开始花了额外时间分析是否系统编码问题，而非命令本身问题。

根因：

Shell 执行模块在捕获子进程异常时，未对异常类型进行“翻译”和“分层”。当遇到非 0 退出码时，它直接抛出内部异常，而不是将子进程的 stderr 作为主要信息。

这导致工具链自身的运行时错误与用户命令错误混在一起，难以区分。

解决思路：

错误分类与翻译：对于 Shell 调用，若子进程退出码非 0，优先返回子进程的 stderr 内容作为错误信息，而不是抛出工具层异常。只有当子进程完全无法启动（如命令不存在）时才报告工具层错误。

增加“错误码映射”：将常见的命令错误（如 command not found、permission denied）映射为人类可读的描述，并在输出中明确标注“这是用户命令的错误，不是工具内部错误”。

总结
这些额外问题属于用户体验、性能、可靠性和可诊断性层面的，虽然不直接影响最终任务的正确性，但严重降低了交互的流畅度和信任感。解决它们不需要重写架构，更多是在工具链的“胶水层”（如错误处理、路径转换、并发控制）增加智能包装，让底层能力以更友好的方式暴露给 Agent。
