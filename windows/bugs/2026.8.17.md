# 工具链问题诊断与改进建议

> 本文基于一次真实会话的执行日志整理，所有问题均可复现或附证据；无法验证的项已明确标注。

---

## P0 — 阻塞级缺陷（本次会话真实发生）

### ~~1. Shell 输出捕获层编码崩溃~~ ✅ DONE

**措施**：PowerShell args 增加 `$OutputEncoding=[Console]::OutputEncoding=[Text.Encoding]::UTF8;chcp 65001 >$ null;` 前缀；
非 UTF-8 输出从硬错误降级为 lossy text + `<system>encoding=lossy</system>` 警告；
`decode_valid_utf8_prefix` 最后 resort 从 `@utf8.decode` 改为 `@utf8.decode_lossy`。
（`agent_tool/internal/platform_shell/platform_shell.mbt`, `agent_tool/shell/shell.mbt`）

### 2. Shell 错误报告语义分层

**现象**：`Malformed` 掩盖了真正的命令错误（如 `tree` 的参数错误），导致诊断方向被误导到"系统编码问题"而非命令本身。

**方案**：
- 子进程退出码非 0 时，优先返回子进程的 stderr 内容作为错误信息；
- 明确区分"工具内部错误"与"用户命令错误"，并标注；
- `command not found` / `permission denied` 等常见错误映射为人类可读描述。

### ~~3. 编辑工具匹配失败诊断增强~~ ✅ DONE

**措施**：`old_string not found` 时返回附近上下文行（锚点 ±2 行）、首个差异字符位置、常见原因提示
（行尾符、全角/半角、tab/space、read 分隔符）。
（`agent_tool/edit/edit.mbt` — `old_string_context` 函数）

## P1 — 高价值增强

### 4. write 工具策略透明化

当前 Agent 对"哪些文件允许 write 覆写"只能靠提示词里零散的文字猜测，面对 `.md` 也畏首畏尾。

**方案**：在工具文档中给出明确策略表：
- 允许 write 覆写：`.md` / `.txt` / `.json` / `.toml` 等非源码文件；
- 必须使用 edit/multi_edit：`.mbt` / `.mbt.md` 等源码文件（有意设计，保源文件）；
- write 被拒时，错误信息中返回允许的文件类型列表。

### 5. multi_edit 可选尽力模式

**现状**：全量原子回滚是有意设计（避免文件 A 改了、文件 B 没改的中间态），且失败项已有回显；但一次匹配失败会导致整批作废。

**方案**：
- 新增 opt-in 参数（如 `ignore_missing`）：跳过匹配失败的项，返回逐项成功/失败结果；**默认仍保持原子性**；
- 增加可选的 diff 预览步骤，提交前可检查再应用。

### ~~6. Windows 子进程静默执行~~ ✅ DONE

**措施**：在三处 `@process.spawn`/`@process.run` 调用新增 `no_console_window=true`：
会话组 shell 执行、单次收集路径、moon 命令执行。与代码库 26+ 处已有用法一致。
（`agent_tool/shell_exec/execution.mbt`, `agent_tool/shell/shell.mbt`, `agent_tool/run_moonbit/run_moonbit.mbt`）

### 7. 任务进度流与心跳

**现象（UI 现状未经验证，属合理假设）**：批量 read / shell 调用期间前端无进度反馈，用户感知为"假死"。

**方案**：工具调用生命周期 `pending → running → finishing → done` 以增量方式推送；单调用超过 5 秒自动发送"仍在处理中"心跳。

### 8. 大规模编辑的策略准则

编辑前先预估改动规模：当改动超过文件总行数约 20%–30%，或涉及 5 个以上不连续块时——
- 文档类文件（`.md` 等）优先用 write 全量重写，避免逐行匹配反复失败的时间与 token 浪费；
- 源码文件优先用 multi_edit 合并批量，以编译器诊断驱动后续修复。

## P2 — 低优先级 / 需谨慎

### 9. 会话级查询缓存与批量执行接口

**风险实证**：本会话中某文件行数 86→85 是编辑动作的结果——对会编辑文件的 Agent，陈旧读比慢读更危险，跨调用缓存会直接返回过期行号。

**方案（如实施）**：
- 查询缓存：仅限纯查询命令、默认关闭；单轮生命周期 + 目录指纹失效 + 任何编辑动作后全量失效；
- 批量执行接口：接受命令数组，在单个子进程内顺序执行并聚合输出，减少 Windows 下进程创建开销；代价是牺牲并行性，适合大量同目录小查询场景。

### 10. 路径格式统一

文件工具内部接受 POSIX 风格路径并自动转换为平台本地路径。纯便利性改进，非痛点。

### 11. 写入时保持文件原有换行风格

编辑器写入前检测文件的既有换行风格（LF / CRLF），写入时保持一致，避免跨平台协作仓库出现整文件 diff 噪音。这是独立的健壮性原则——本会话的匹配失败与换行符无关，但不影响该原则本身的价值。

---

## 明确不采纳

- **编辑匹配引入模糊匹配 / 归一化比较层**：对代码编辑工具，模糊匹配引入的歧义风险大于收益；真实问题靠 P0-3 的诊断增强即可解决。
- **换行符自动归一化作为匹配失败修复**：非本案根因（文件为 UTF-8，含中文多行匹配成功）；若未来实施，必须保留文件原换行风格，避免破坏团队约定格式。

---

## 结语

改进方向不是让工具更"智能"，而是让工具在底层更健壮、反馈更明确、策略更清晰：
- 文档与源码解耦编辑策略（该灵活时灵活，该严格时严格）；
- Windows 与 Unix 解耦执行环境；
- 让 Agent 基于确定性规则决策，而不是反复试错。

## 附录：关键证据

### A. `Malformed` 与输出内容的相关性

```
仅 ASCII 输出 → 成功：
  [System.IO.File]::ReadAllLines(".../01-project-overview.md").Length  → 85 ✓
  [System.IO.File]::ReadAllBytes("...")[0..10]                        → 字节序列 ✓

含中文输出 → Malformed：
  tree research/ /F
  Select-String -Pattern "providers" -Path "research/03-module-structure.md"
  [System.IO.File]::ReadAllLines("...")[12] -join "|"

ASCII 错误文本 → 正常透传：
  InvalidArgument: Cannot convert value ":" to type "System.UInt64" ✓
```

### B. `old_string not found` 的真实原因

```
失败项（无一例外以 || 开头——多抄了一个 markdown 表格分隔符）：
  "|| `moon.mod.json` | 包清单，声明名称和版本 |"      ✗
  "|| Providers | `providers/` | ⚙️ | Provider构造函数 |"  ✗

成功项（多行、含中文，一次成功）：
  "├── providers/               # Provider构造函数
   ├── authentication/          # 认证API"              ✓
```

read 工具的显示格式是"行号 |内容"；markdown 表格行内容本身以 `|` 开头，构造 old_string 时把显示分隔符一并抄入，导致每个失败项多了一个 `|`。

### C. 已有机制清单（不必重复建设）

- write 拒绝覆写 `.mbt` / `.mbt.md` 是有意设计；`.md` 等文档文件允许覆写；
- edit / write 写入前有语法门禁（moonc syncheck），可配置在引入解析错误时拒绝写入；
- multi_edit 除原子回滚外，已有失败项回显与"编译错误增长自动回滚"保护。
